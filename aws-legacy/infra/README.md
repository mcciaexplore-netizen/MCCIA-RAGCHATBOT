# Sampada infrastructure (Phases 2, 5, 6)

AWS CDK (Python) app that creates:

- An S3 bucket (`ArchiveBucket`) for `raw/` PDFs and `processed/` articles.
  Name is auto-generated by CDK unless you pass `-c bucket_name=<name>` with
  a name you've already confirmed is globally free — `sampada-archive` in
  the spec is illustrative, not reserved.
- A Bedrock **VectorKnowledgeBase** using **Titan Text Embeddings V2**
  (1024-dim), via the AWS Labs `cdklabs.generative-ai-cdk-constructs`
  library (`bedrock.VectorKnowledgeBase`). No `vector_store` is passed, so
  the construct provisions a brand-new **OpenSearch Serverless** collection
  and vector index itself — this is what the spec means by "Bedrock's
  default managed option, no separate provisioning": we're not hand-rolling
  the OpenSearch Serverless security policies/index ourselves, the construct
  does it the same way the Bedrock console's "Quick create" flow would.
- An **S3 data source** on that KB scoped to `processed/` only (`raw/` PDFs
  are deliberately excluded from embedding), with fixed-size chunking at
  ~300 tokens / 20% overlap, matching the spec.
- The Next.js app's own IAM role (`SampadaAppRole`): `bedrock:Retrieve` +
  `bedrock:RetrieveAndGenerate` on the knowledge base, plus `s3:GetObject`
  on exactly one key, `index/issues.json` (the archive browse page's data
  source — Bedrock's retrieve APIs aren't built for an exhaustive
  chronological listing, so that page needs a real index; this was a
  deliberate, narrow exception to "nothing broader than Bedrock", agreed on
  with you in Phase 5). It's an Amplify Hosting **SSR compute role**, not a
  generic IAM role — its trust policy allows `amplify.amazonaws.com` to
  assume it, confirmed against AWS's docs. This role isn't attached to an
  Amplify App by CDK here, since that needs a real git remote we don't have
  yet (Deployment step) — its ARN (`AppRoleArn` output) is what you'll paste
  into that app's Compute role setting once it exists.
- **Phase 6 — `KeepCurrentFunction`**: a Python Lambda (bundled from
  `../ingest`, same code Phase 1 runs locally) on a weekly `EventBridge`
  schedule. It pulls state (manifest, index, manual-review log) from
  `s3://<bucket>/state/` since Lambda's `/tmp` doesn't survive between
  invocations, runs `ingest.run_pipeline.cmd_all` exactly as a local `all
  --upload` would, pushes state back, then checks mcciapunesampada.com's
  Blogger "Pages" feed for any issue not yet in our index (logged, not
  auto-ingested — see `ingest/check_web_archive.py`'s docstring for why
  guessing issue-page URLs doesn't work reliably on that site). Its role
  gets read/write on the whole bucket (this is the ingestion pipeline's own
  execution role, not the read-only app role above — no "nothing broader"
  constraint applies to it), read on a `DriveCredentialsSecret` (Secrets
  Manager, placeholder value until you fill it in), and Bedrock
  `InvokeModel`/`StartIngestionJob`/`GetIngestionJob`.

## Verified, but not yet deployed

I installed this exact library locally and instantiated the stack to
confirm the constructor signatures, defaults, and grant methods used here
are real (not guessed) — `VectorKnowledgeBase`, `add_s3_data_source`,
`ChunkingStrategy.fixed_size`, `BedrockFoundationModel.TITAN_EMBED_TEXT_V2_1024`,
and `grant_retrieve`/`grant_retrieve_and_generate` all exist with the
signatures used in `sampada_stack.py`. `cdk synth` gets as far as bundling
the Lambda-backed custom resource that creates the OpenSearch vector index
(confirming our construct usage is structurally valid) and then fails only
because **this environment has no Docker daemon**, which CDK needs to bundle
that Lambda's dependencies. That's a normal one-time requirement on whatever
machine actually deploys this (Docker Desktop, or Finch/Podman via the
`CDK_DOCKER` env var) — nothing about our stack code is blocked on it. A
real `cdk synth`/`cdk deploy` still needs to be run on a machine with Docker
and real AWS credentials before this is confirmed end-to-end.

The Phase 6 Lambda (`PythonFunction`) hits the exact same Docker wall for
its own dependency bundling (it needs to pip-install PyMuPDF etc. for
Lambda's Linux runtime, which local macOS wheels can't satisfy) — so it's
never actually constructed in this environment's `cdk synth` either. What I
could verify without Docker: I built an isolated test stack with a stub
`lambda.Function.from_function_attributes(...)` standing in for the real
one, and confirmed the `EventBridge Rule` + `LambdaFunction` target,
`Secret` + `grant_read`, `Bucket.grant_read_write`, and both
`add_to_role_policy` IAM statements all construct without error against
that stub — i.e. the wiring around the Lambda is sound, only the Lambda's
own asset bundling is unverified here.

**Stability note**: `cdklabs.generative-ai-cdk-constructs` marks
`VectorKnowledgeBase` as `(experimental)`. It's an official AWS Labs
library and the standard way this exact stack (Bedrock KB + OpenSearch
Serverless) is built in CDK today, but experimental means its API can
change between minor versions — pin the version (already done in
`requirements.txt`) and re-check the changelog before upgrading it.

## Prerequisites to actually deploy

1. AWS credentials for the target account, `ap-south-1`.
2. Docker running locally (asset bundling, as above).
3. `cdk bootstrap aws://<account-id>/ap-south-1` — one-time per account/region.
4. Titan Text Embeddings V2 and your chosen Claude model both need **model
   access enabled** in the Bedrock console for this account/region before
   the KB will actually embed anything or generate answers.

## Deploy

```bash
cd sampada/infra
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
npx aws-cdk@2 bootstrap aws://<account-id>/ap-south-1   # first time only
npx aws-cdk@2 diff
npx aws-cdk@2 deploy
```

Take the `ArchiveBucketName` output and put it in `sampada/.env` as
`S3_BUCKET` so Phase 1's ingestion pipeline uploads to the right place.

For `sampada/web/.env.local`: `KnowledgeBaseId` -> `BEDROCK_KNOWLEDGE_BASE_ID`,
`ArchiveBucketName` -> `S3_BUCKET` (only used there to read
`index/issues.json`). `AppRoleArn` is what gets attached as the Amplify
app's Compute role once one exists.

### After deploy: three things the Lambda still needs

CDK can't know these ahead of time (a real Drive folder, a granted
inference profile, a real credential) -- fill them in once, after `deploy`:

```bash
# 1. The Drive service account key (Secrets Manager, empty placeholder until now)
aws secretsmanager put-secret-value \
  --secret-id "$(aws cloudformation describe-stacks --stack-name SampadaStack \
      --query "Stacks[0].Outputs[?OutputKey=='DriveCredentialsSecretArn'].OutputValue" --output text)" \
  --secret-string file://drive-service-account.json

# 2 & 3. The real Drive folder ID and Bedrock inference profile ARN
aws lambda update-function-configuration \
  --function-name "$(aws cloudformation describe-stacks --stack-name SampadaStack \
      --query "Stacks[0].Outputs[?OutputKey=='KeepCurrentFunctionName'].OutputValue" --output text)" \
  --environment "Variables={GOOGLE_DRIVE_ROOT_FOLDER_ID=<real-folder-id>,BEDROCK_ARTICLE_SPLIT_MODEL_ID=<real-inference-profile-arn>}"
```

(`update-function-configuration` replaces the whole `Variables` map, so if
you ever hand-edit other env vars in the console, re-include them here too —
redeploying the stack afterwards restores CDK's version regardless.)
